# Deploy s1d1-tantive on Heroku

This page shows how to deploy s1d1-tantive on Heroku with the Deploy button. Three files make it: `app.json` and
`heroku.yml` at the root of the repository, and `deploy/heroku/Dockerfile`, a single
`FROM ghcr.io/scombat/s1d1-tantive:0.6.0-small-onnx-int8` with an `ENTRYPOINT` that starts the service on Heroku's
`$PORT`. `app.json` sets `"stack": "container"`, so Heroku builds that Dockerfile instead of using a buildpack.

[![Deploy](https://www.herokucdn.com/deploy/button.svg)](https://www.heroku.com/deploy?template=https://github.com/scombat/s1d1-tantive)

The button needs the repository to be public. Checked on devcenter.heroku.com on 2026-10-21.

## Facts

- Image: `ghcr.io/scombat/s1d1-tantive:0.6.0-small-onnx-int8`
- RAM: 1024 MiB (Standard-2X dyno, 1 GB, checked 2026-10-21)
- Status: needs public repository
- Still to do (you): make the repository public; the images are already public.

## Free tier and variant

Heroku has no free tier. The Cedar dynos (dyno-types, 2026-10-21): Eco 0.5 GB at $5 a month for a pool of 1,000 hours,
Basic 0.5 GB at $7, Standard-1X 0.5 GB at $25, **Standard-2X 1 GB at $50**, Performance-M 2.5 GB at $250. The button
therefore asks for a **Standard-2X** dyno (`formation.web.size`: `standard-2x`), the smallest one that holds the
`small` variant (1 GiB needed). The `tiny` variant (512 MiB needed, about 450 MiB idle) would run on Eco or Basic,
but with a margin so small that Heroku's memory quota (R14) could be hit under load; to try it, change the tag in
`deploy/heroku/Dockerfile` and `size` in `app.json` together. The `full` variant (2 GiB) needs Performance-M.

## Variables to set

- `S1D1_TIERS` is required with no default: give the tier names your gateway sends, otherwise the service answers 422.
- `S1D1_API_KEY` is generated by Heroku (`generator: secret`) because the app URL is public: read it with
  `heroku config:get S1D1_API_KEY -a <app>` and send it as `Authorization: Bearer <key>`.
- `S1D1_FORMATS` and `S1D1_DEADLINE_MS` have defaults; `PORT` is set by Heroku and mapped to `S1D1_PORT` by the
  `ENTRYPOINT` (the base image's own `ENTRYPOINT` is replaced, so a `CMD` alone would only be passed to it as
  arguments).
- Readiness: Heroku has no readiness path for containers (`HEALTHCHECK` is unsupported, `app.json` has no health
  check key). The service listens only once the model has loaded, so the router sends traffic only when `/ready`
  would answer 200; Heroku's own boot timeout applies to that load (a few seconds for `small`).
- `app.json` is read only when the app is created; later changes to it do not affect existing apps.

## Caveats

- The button creates Cedar-generation apps; the Fir generation cannot be created from a button.
- Heroku builds its own image from the Dockerfile, so only the build's `FROM` pulls the published (OCI) image. No page
  of the Dev Center shows a button building from `heroku.yml` end to end: the first real deployment is the test.

## Deploy by hand

```bash
heroku create s1d1-tantive --stack container
heroku config:set S1D1_TIERS="TRIVIAL=0.15,LOW=0.4,MEDIUM=0.7,HIGH=0.9,EXPERT=1.0" S1D1_API_KEY=<key> -a s1d1-tantive
heroku ps:type web=standard-2x -a s1d1-tantive
git push heroku main      # builds deploy/heroku/Dockerfile named by heroku.yml
```

## Terraform

One file, `deploy/heroku/terraform/main.tf` (provider `heroku/heroku`): the app on the container stack, a build of this
repository's `heroku.yml` from a tarball URL, and the web formation. Heroku cannot pull an image, so the repository must be
public. Not applied here (no Heroku account).
